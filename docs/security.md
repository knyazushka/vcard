# Безопасность

## Аутентификация

**Access** — JWT (HS256), 15 минут, в теле ответа. Внутри только `sub`
(пользователь) и `sid` (цепочка сессии).

**Refresh** — 32 случайных байта, в httpOnly-cookie. В базе лежит только sha256.

```
vcard_refresh=<opaque>; HttpOnly; Secure; SameSite=Lax; Path=/api/v1/auth
```

`Path` сужен до `/auth`: на остальные запросы cookie не ходит вовсе, и XSS
на странице профиля до неё не дотянется. `SameSite=Lax` достаточно, потому что
refresh обменивается только методом POST, а Lax запрещает межсайтовые POST.

Фронту: **access держать в памяти JS, не в localStorage**. Тогда XSS крадёт
15 минут, а не постоянный доступ.

### Фронт на другом поддомене

Фронт (`vc.…`) и API (`vc-api.…`) — разные origin, но один site: регистрируемый
домен общий. Отсюда два следствия.

- `SameSite=Lax` не мешает: запрос с фронта на API браузер считает
  same-site, и cookie уходит в том числе с POST. Атрибута `Domain` у cookie
  нет — она привязана только к хосту API, фронту читать её незачем.
  Запросы к `/auth/**` фронт делает с `credentials: 'include'`.
- Нужен CORS. Origin сверяется с точным списком `CORS_ALLOWED_ORIGINS`,
  маски и отражение пришедшего `Origin` запрещены: вместе
  с `Allow-Credentials` это дало бы любому сайту обменять refresh-cookie
  посетителя на access-токен. Список проверяется на старте — origin
  со слэшем в конце иначе молча не совпал бы ни с одним запросом.

### Почему refresh не JWT

Подписанный токен отозвать невозможно, а отзыв — единственное, ради чего refresh
существует.

### Почему в токене нет роли

Роль и компания резолвятся на каждом запросе. Иначе исключение сотрудника
вступало бы в силу через 15 минут, а при тенантной модели это уже доступ
к чужим данным.

Цена: отзыв access не мгновенный. Мгновенный потребовал бы проверки `sid`
по хранилищу на каждом запросе, то есть отказа от stateless.

### Обнаружение кражи refresh

Токены ротируются при каждом обмене. Предъявление **уже израсходованного**
токена означает, что у него была копия: легитимный клиент так не может,
он уже получил замену. Гасится вся цепочка сессий, а не предъявленный экземпляр.

Жертва при этом тоже разлогинивается — осознанная цена за то, что кража
не остаётся незамеченной.

### Пароли

argon2id, параметры хранятся внутри строки хэша (формат PHC), поэтому
ужесточение настроек не обесценивает старые пароли.

Не bcrypt: он молча обрезает вход на 72 байтах, и при разрешённых 128 символах
часть пароля не участвовала бы в проверке — без единого признака в логах.

Сравнение хэшей — за постоянное время.

## Что не рассказывается наружу

| Ситуация | Ответ |
|---|---|
| неверный пароль / нет такого адреса | одинаковый 401 |
| чужой или несуществующий ресурс | одинаковый 404 |
| токен приглашения: неизвестен / отозван / принят / истёк | одинаковый 404 |
| причина отказа аутентификации | всегда «войдите» |

Вход по несуществующему адресу **всё равно считает хэш** — иначе по времени
ответа перебираются зарегистрированные почты.

Наружу уходит только машиночитаемый `code`; текст ошибки с именами таблиц
и значениями полей остаётся в логе, связь — по `requestId`.

## Ограничение частоты

Лимит на адрес клиента, token bucket: в минуту — не больше лимита, но весь
лимит доступен и разом, так что быстрый человек не упирается в стык минут.

| | По умолчанию | Операции |
|---|---|---|
| строгий | 10 в минуту на каждую операцию (`RATE_LIMIT_STRICT_PER_MINUTE`) | вход, регистрация, просмотр и приём приглашения, отправка и повтор приглашения |
| общий | 100 в минуту (`RATE_LIMIT_PER_MINUTE`) | всё остальное API |

Строгий лимит — не про нагрузку, а про перебор: на входе и приёме приглашения
подбирают пароли и токены, а приглашения уходят письмами с нашего домена.
Сотни попыток в минуту с одного адреса общий лимит пропустил бы.

- Строгий лимит у каждой операции свой: администратор, разославший десяток
  приглашений, не теряет заодно возможность войти.
- Отказ — `429` с `Retry-After` и телом `Error` с кодом `rate_limited`,
  как у любой другой ошибки API.
- Адрес — тот же, что попадает в список сессий: `X-Forwarded-For` учитывается
  только за доверенным прокси, подменой заголовка лимит не обойти.
- IPv6 считается по `/64`: столько адресов у одного абонента.
- `/files` не ограничивается: файлы неизменны и кэшируются браузером,
  а список сотрудников тянет десятки аватарок за одну загрузку страницы.
- Корзины в памяти процесса: при нескольких репликах лимит умножается на их
  число.

**Фронту:** SSR-запросы к API идут с адреса сервера фронта, и для лимита
все посетители публичных страниц будут одним клиентом. Когда фронт появится,
он должен ходить в API по внутренней сети с `X-Forwarded-For` посетителя —
либо его адрес надо исключить из лимита.

## Изоляция тенантов

`company_id` — обязательный аргумент в каждом методе репозитория, а не
опциональный фильтр, который забудут передать. Роль проверяется на каждом
запросе; для чужой компании ответ — 404.

Тег из чужого справочника не подставится: принадлежность компании сверяется
в самом запросе вставки.

Тенант определяется **путём** (`companyId` в маршруте), а не заголовком.
Заголовок активного тенанта был бы вторым источником истины и рано или поздно
разошёлся бы с путём.

## Пользовательский HTML

«Обо мне» приходит из редактора в браузере — то есть полностью под контролем
пользователя. Очистка `bluemonday` **на записи**, allowlist: `p`, `br`, `b`,
`strong`, `i`, `em`, `u`, `h2`, `h3`, `ul`, `ol`, `li` плюс классы `ql-*`
редактора Quill.

Ссылки в allowlist не входят: «Обо мне» — описание человека, а произвольный
`href` превращает каждую визитку в площадку для рассылки.

Письма: текстовая часть собирается `text/template`, HTML — `html/template`.
Только второй экранирует подстановки, а название компании приходит
от пользователя.

## Загрузка файлов

- Тип определяется **по сигнатуре содержимого**, а не по `Content-Type`
  и не по расширению — и то и другое задаёт клиент.
- Размер ограничивается на чтении (аватар 5 МБ, логотип 2 МБ), а не по
  заголовку `Content-Length` — он тоже клиентский.
- Имя файла в хранилище — хэш содержимого, исходное имя не используется.
- Ключи объектов очищаются от `..`, итоговый путь сверяется с корнем
  хранилища.
- Раздача ставит `X-Content-Type-Options: nosniff`: подобранный браузером
  `text/html` на пользовательском файле — это XSS.

## Ссылки в письмах

Собираются **только** из `PUBLIC_APP_URL`, никогда из заголовка `Host`
входящего запроса. Иначе подделанный `Host` уезжает в письмо жертве вместе
с нашим текстом и чужой ссылкой.

Токен приглашения существует единственный раз — в письме. Повторная отправка
всегда выпускает новый токен и гасит прежний.

## Логи

`X-Request-Id` из входящего запроса принимается только за доверенным прокси
(`TRUST_PROXY_HEADERS`) и в любом случае обрезается по длине и алфавиту:
иначе клиент управляет содержимым наших логов, включая переводы строк.

Путь приёма приглашения маскируется — в нём стоит одноразовый токен, и запись
его в журнал доступа равносильна хранению учётных данных открытым текстом.

## Прод: секреты и доступ

- **Секреты** — только в окружении `production` в GitHub. В репозитории
  их нет, на сервере они не хранятся между выкатками: job выкатки собирает
  `app.env` и `grafana.env` заново и кладёт с правами 600. В скрипт workflow
  значения передаются через `env`, а не подстановкой `${{ }}` в текст
  команды — содержимое секрета не может стать командой.
- **Вход CI на сервер** — отдельный ключ и отдельный пользователь `deploy`:
  отзывается, не трогая администратора. Ключ сервера закреплён в
  `SSH_KNOWN_HOSTS`, а не принимается при первом подключении — иначе
  подменённый хост получил бы все секреты.
- **Реестр образов** — `GITHUB_TOKEN` конкретного запуска: живёт, пока идёт
  job, передаётся на stdin, после выкатки — `docker logout`.
- **Снаружи** открыты только 80 и 443 (Caddy) и 22. Порт api 8080 доступен
  лишь Caddy во внутренней сети compose; пробы и метрики (9090) и Grafana
  (3000) — только на `127.0.0.1` сервера, Grafana — через SSH-туннель.
- **Образ** — distroless, без шелла и пакетного менеджера, процесс
  не от root. `.env` исключён из контекста сборки.

## Незакрытые долги

Это **не** «когда-нибудь», а список того, что осознанно не сделано:

1. **Лимит только по адресу.** Перебор паролей одного аккаунта с сотни адресов
   он не остановит — для этого нужен ещё лимит по почте на входе. Администратор
   компании может разослать до `RATE_LIMIT_STRICT_PER_MINUTE` приглашений
   в минуту; суточного потолка на компанию нет.
2. **Ротации ключа подписи JWT нет** — один секрет, без `kid` в заголовке
   токена. Ротация без `kid` означает даунтайм.
3. **Протухшие сессии не чистятся.** Метод `DeleteExpired` написан, воркер,
   который его зовёт, — нет. Таблица растёт с каждым входом.
4. **`COOKIE_SECURE` можно опустить.** По умолчанию поднят; опускать — только
   осознанно и только локально.
