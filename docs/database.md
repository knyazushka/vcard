# База данных

PostgreSQL 18. Миграции — goose, вкомпилированы в бинарь через `go:embed`.

## Таблицы

```
users ──┬── sessions            цепочки refresh-токенов
        ├── memberships ──── companies ──┬── company_phones
        │                                 ├── positions   ┐ справочники
        │                                 ├── tags        ┘ тенанта
        │                                 └── invitations
        └── profiles ──── profile_tags
reserved_slugs      служебные адреса, которые нельзя занять
email_outbox        очередь исходящих писем
```

## Ключевые решения схемы

### Почта и слаги — `citext`

Регистронезависимость нужна по смыслу: `Ivan@acme.com` и `ivan@acme.com` —
один человек, `/employee/Laura` и `/employee/laura` — одна страница. Длина
ограничена `CHECK`, а не типом: уменьшить `varchar(n)` можно только переписав
таблицу под эксклюзивной блокировкой.

### Слаг уникален безусловно

```sql
slug citext not null unique
```

Без partial-условия намеренно: по ТЗ блокировка страницы адрес **не
освобождает**. То же и для архивных профилей.

Служебные адреса (`admin`, `api`, `employee`, `login`, …) лежат в
`reserved_slugs` и проверяются триггером — список пополняется без релиза.

### Роль принадлежит связке, а не пользователю

`memberships(user_id, company_id, role)`. Один человек бывает администратором
в одной компании и рядовым сотрудником в другой.

Везде `text` + `CHECK` вместо enum-типов: значение в enum добавить легко,
а переименовать или убрать — только пересозданием типа со всеми зависимостями.

### Компания не остаётся без администратора

Отложенный constraint-триггер `memberships_keep_admin`. Проверка в базе,
а не в коде, потому что два одновременных понижения по отдельности выглядят
допустимыми, а вместе лишают компанию управления.

`DEFERRABLE INITIALLY DEFERRED` — чтобы внутри одной транзакции можно было
передать администрирование в любом порядке.

### Не больше трёх тегов — без триггера

```sql
sort_order smallint not null check (sort_order between 0 and 2),
primary key (profile_id, sort_order)
```

Потолок задан структурой: четвёртая строка физически не вставляется. Тот же
приём для десяти телефонов компании.

«Ровно три для публикации» проверяет домен: у черновика их может быть меньше.

### Нормализация справочников — генерируемый столбец

```sql
title_norm text generated always as (
    lower(btrim(regexp_replace(title, '\s+', ' ', 'g')))
) stored
```

плюс уникальный индекс по `(company_id, title_norm)`. Правило нельзя обойти
ни из psql, ни из миграции — «Golang», «golang» и «  GoLang » не попадут
в один справочник.

### Удаление из справочника не ломает чужие визитки

`BEFORE DELETE`-триггеры переносят название в профиль: ссылка превращается
в пользовательское значение. `ON DELETE SET NULL` здесь не годится — он обнулил
бы одну колонку из пары и нарушил XOR-констрейнт.

### Кроп аватара — метаданные, а не файл

`avatar_crop_x/y/size` рядом с `avatar_key`. Исходник остаётся целым, и область
можно переиграть, не заставляя человека загружать фотографию заново. Задаётся
целиком или не задаётся вовсе — это стережёт `CHECK`.

### Приглашения: нет статуса `EXPIRED`

Истечение вычисляется при чтении (`expires_at < now()`). Иначе состояние строки
зависело бы от того, жив ли воркер, и приглашение считалось бы действующим,
пока его не удосужились пометить.

Одно действующее приглашение на адрес — частичный уникальный индекс
`where status = 'PENDING'`. Отозванное или принятое не мешает пригласить заново.

В базе лежит **sha256 токена**, а не токен: утечка дампа не даёт вступить
ни в одну компанию.

### Собственные коды ошибок

Триггеры поднимают исключения с кодами `VC001` (компания осталась бы без
администратора) и `VC002` (адрес зарезервирован). Приложение сопоставляет код,
а не текст сообщения, который меняется при первой правке формулировки.

Разбор SQLSTATE — `internal/repository/postgres/errors.go`.

## Правила работы с миграциями

- **Никогда не править применённую миграцию** — только добавлять новую.
  Пример: смена кодов ошибок сделана отдельным файлом `00008`, хотя правились
  функции из `00003` и `00005`.
- **Down-секция обязательна и должна работать.** Проверяется командой
  `make migrate-verify`: вверх → полный откат → снова вверх. Это ловит то,
  чего обычный `up` не видит: неработающие откаты, порядок удаления объектов,
  зависимости триггеров и функций.
- **Функции и триггеры — внутри `-- +goose StatementBegin/End`**, иначе goose
  разрежет их по точке с запятой.
- Миграции накатываются **отдельным шагом релиза**, а не при старте приложения:
  иначе три пода на выкатке дерутся за схему.

## Команды

```bash
make db-up            # поднять Postgres и Mailpit
make migrate-up       # накатить
make migrate-status   # что применено
make migrate-verify   # вверх → сброс → вверх, проверка обеих сторон
```

Строка подключения по умолчанию — `postgres://vcard:vcard@localhost:5433/vcard`.
Порт **5433**, а не 5432: на стандартном обычно уже слушает локально
установленный Postgres, и перепутать окружение проекта с чужой базой слишком
легко.
