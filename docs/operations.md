# Эксплуатация

## Двенадцать факторов

Не декларация, а список конкретных следствий в коде.

| | Как сделано |
|---|---|
| **I. Кодовая база** | один репозиторий, два бинаря из одного модуля и одного образа — версия схемы и версия кода не расходятся |
| **II. Зависимости** | `go.mod`; ogen, goose и golangci-lint закреплены `tool`-директивами; версии образов закреплены |
| **III. Конфигурация** | только окружение, `internal/config` — единственное место с доступом к нему. В разработке — `.env`, в проде — окружение `production` в GitHub |
| **IV. Сторонние сервисы** | Postgres, SMTP, S3 — за интерфейсами, адреса из окружения |
| **V. Сборка/релиз/запуск** | образ собирает CI; миграции отдельным бинарём и отдельным шагом, **не при старте приложения** |
| **VI. Процессы** | сессии в базе, файлы и кэш карточек в S3 — процесс stateless |
| **VII. Привязка портов** | `net/http` слушает сам, никакого веб-сервера внутри контейнера |
| **VIII. Масштабирование** | вторую реплику можно поднять без правок кода; оговорки — в «Масштабировании» |
| **IX. Утилизируемость** | корректная остановка по SIGTERM с таймаутом |
| **X. Паритет сред** | в разработке те же Postgres и SMTP; прод-стенд целиком поднимается локально из тех же файлов, что на сервере |
| **XI. Логи** | `log/slog` в stdout, JSON в проде, текст в разработке. Ни файлов, ни ротации |
| **XII. Управляющие задачи** | миграции — подкоманды того же модуля, не отдельные скрипты |

## Порты

| Порт | Что |
|---|---|
| `8080` | API (`/api/v1/**`) и файлы (`/files/**`) |
| `9090` | `/healthz`, `/readyz`, `/metrics` — наружу не публиковать |

## Пробы

- **`/healthz`** — процесс жив. **В базу не ходит намеренно:** проверка
  зависимостей здесь означала бы, что кратковременная недоступность Postgres
  заставляет оркестратор перезапускать совершенно здоровые процессы.
- **`/readyz`** — можем обслуживать прямо сейчас, с проверкой базы. По нему
  скрипт выкатки решает, что новая версия поднялась.

## Порядок выкатки

```
1. migrator up
2. api          только после успешной миграции
```

Миграции обязаны быть совместимы с **предыдущей** версией кода: пока идёт
миграция, работает ещё старый процесс, а при откате новая схема остаётся
под старым кодом.

## Прод

```
 :443 ──▶ Caddy ─┬─ vc-api ──────────────▶ api:8080 ─┬─▶ Postgres   управляемый, приватная сеть
                 ├─ vc /api/v1/* ────────▶ api:8080  └─▶ S3         приватный бакет
                 └─ vc  остальное ─▶ web:3000 ──▶ api:8080   серверный рендер
 127.0.0.1:9090 ──▶ api:9090      пробы и метрики, только с самого сервера
 127.0.0.1:3000 ──▶ Grafana ──▶ Prometheus ──▶ api:9090
```

`web` — фронт из репозитория `vcard-app`: свой CI, свой compose-проект
`vcard-web` в `/opt/vcard-web`, подключённый к сети этого, `vcard_default`.
Его домен обслуживает этот же Caddy, поэтому бек выкатывается первым.
Обе выкатки берут один замок на сервере и не идут одновременно.

Одна VPS в Timeweb.Cloud с Docker Compose, рядом — управляемый Postgres
и S3. Почему так, а не App Platform или Kubernetes, — в
[решениях](decisions.md) (18).

Важного состояния на сервере нет: база управляемая, файлы в S3. На диске
только сертификаты Caddy и история метрик — их потеря не страшна. Сервер
можно пересоздать и выкатить заново.

- **Caddy** сам получает и продлевает сертификат Let's Encrypt, выставляет
  `X-Forwarded-For` и собственный `X-Request-Id` — поэтому
  `TRUST_PROXY_HEADERS=true`. Порт 8080 наружу не опубликован.
- **Файлы** отдаёт `/files` из приватного бакета: `STORAGE_BASE_URL`
  указывает на API. Ключи — хэши содержимого, браузер кэширует их навсегда,
  так что до сервера доходит только первый запрос.
- **`:9090`** опубликован только на `127.0.0.1` — по нему скрипт выкатки
  ждёт готовности.

Всё, что нужно на сервере, лежит в [`deploy/`](../deploy) и копируется туда
при каждой выкатке. Руками на сервере ничего не правят.

### Домены

Фронт и API — на разных поддоменах, почта — на третьем:

| Имя | Что | Записи |
|---|---|---|
| `vc-api.knyazushka.ru` | API | A → IP сервера. **До** первой выкатки, иначе Caddy не получит сертификат |
| `vc.knyazushka.ru` | фронт | A → IP сервера. Тоже до первой выкатки: без записи Caddy повторяет выпуск сертификата с растущей паузой — API это не задевает, но фронт не откроется |
| `vcard.knyazushka.ru` | отправитель писем | SPF, DKIM, DMARC — см. «Почта» |

### Первая выкатка

Порядок, в котором всё заводится с нуля:

1. **Timeweb.Cloud**, все ресурсы в одном регионе:
   - VPS: Ubuntu 26.04 или Debian 13 (вкладка «Операционные системы», не
     «Docker Hub»), 1 vCPU и 2 ГБ. Меньше — тесно: argon2id берёт 64 МБ
     на каждую проверку пароля, api после нескольких входов держит около
     200 МБ, у Prometheus, Grafana и фронта потолок по 512 МБ.
   - Postgres — см. «База».
   - S3: **приватный** бакет и ключи к нему.
2. **DNS**: A-записи `vc-api` и `vc` на IP сервера.
3. **Сервер** — см. «Подготовка сервера».
4. **GitHub** → Settings → Environments → `production`: секреты
   и переменные из «Конфигурации».
5. Слить в `main` и смотреть Actions → release.
6. Проверить: `curl https://vc-api.knyazushka.ru/api/v1/auth/me` отвечает
   401 в формате `Error`; Grafana — через SSH-туннель (см. «Мониторинг»).

Почта для первой выкатки не обязательна, но до её настройки приглашения
не отправлять: письмо за шесть неудачных попыток — около минуты — уходит
в `FAILED`.

До покупки всего этого стенд целиком проверяется локально — см. «Локальный
прод-стенд».

### Подготовка сервера

Один раз, под root:

```bash
curl -fsSL https://get.docker.com | sh

adduser --disabled-password --gecos '' deploy
usermod -aG docker deploy
install -d -o deploy -g deploy -m 750 /opt/vcard
install -d -o deploy -g deploy -m 750 /opt/vcard-web   # фронт

install -d -o deploy -g deploy -m 700 /home/deploy/.ssh
echo 'ssh-ed25519 AAAA… ci@vcard' > /home/deploy/.ssh/authorized_keys
chown deploy:deploy /home/deploy/.ssh/authorized_keys
chmod 600 /home/deploy/.ssh/authorized_keys
```

Ключ для CI — отдельная пара, не ваш личный: `ssh-keygen -t ed25519 -f
vcard-deploy -N '' -C ci@vcard`. Публичная половина — в `authorized_keys`,
приватная — в секрет `SSH_PRIVATE_KEY`. Отпечаток сервера для
`SSH_KNOWN_HOSTS` — `ssh-keyscan -t ed25519 <IP>`; сверить его с тем, что
показывает консоль сервера в панели, а не принимать на веру.

Группа `docker` — это фактически root. Пользователь `deploy` нужен не ради
прав, а чтобы ключ CI нельзя было использовать как вход администратора
и отозвать его, не трогая ваш.

Снаружи открыты только 22, 80, 443 и 443/udp (HTTP/3) — в облачном
firewall, вход по SSH только по ключу.

### База

- Та же мажорная версия, что в разработке (18).
- Первая миграция создаёт расширение `citext`. Если у пользователя
  управляемой базы нет права на `create extension`, его надо включить
  в панели заранее — иначе выкатка упадёт на первом же шаге.
- Доступ только из приватной сети сервера, без публичного адреса.
- Хватит самого маленького тарифа.

### Почта

Письма отправляет транзакционный почтовый сервис, а не сервер: исходящий
порт 25 у облачных хостеров обычно закрыт, а у свежего IP нет репутации,
и письма уходили бы в спам. Сервис — любой, что принимает российские карты
(например, Yandex Cloud Postbox или Unisender Go).

- **Отправитель** — `no-reply@vcard.knyazushka.ru`, отдельный поддомен:
  репутация рассылки не задевает основной домен.
- **DNS** для `vcard.knyazushka.ru` — значения выдаёт сервис:

  | Запись | Где |
  |---|---|
  | SPF | TXT на `vcard.knyazushka.ru` |
  | DKIM | TXT или CNAME на `<селектор>._domainkey.vcard.knyazushka.ru` |
  | DMARC | TXT на `_dmarc.vcard.knyazushka.ru`; начать с `p=none`, потом ужесточить |

  A и MX для этого поддомена не нужны. Если сервис просит запись для
  возвратов (return-path) — добавить и её.
- **Порт 587**, STARTTLS. `net/smtp` не умеет неявный TLS, поэтому 465
  не заработает без правки кода.
- **`MAIL_FROM` — голый адрес**, без имени вида `Визитки <…>`: он же уходит
  адресом конверта SMTP.
- Проверить с сервера, что порт 587 почтового сервиса доступен —
  хостеры закрывают и его.

### Конфигурация

Разработка — `.env` через `make run`. Прод — окружение `production`
в GitHub (Settings → Environments): job выкатки собирает из него `app.env`
и `grafana.env` и кладёт на сервер с правами 600. Сам сервер конфигурацию
не хранит — править её там бесполезно, следующая выкатка перезапишет.

**Secrets** — то, что нельзя показывать. После сохранения GitHub их
не показывает, так что исходные значения держите в менеджере паролей:

| | |
|---|---|
| `DATABASE_URL` | строка подключения к управляемой базе |
| `JWT_SECRET` | `openssl rand -hex 32`; смена разлогинит всех |
| `STORAGE_S3_ACCESS_KEY`, `STORAGE_S3_SECRET_KEY` | ключи бакета |
| `SMTP_USER`, `SMTP_PASSWORD` | почтовый сервис; пока его нет — не задавать |
| `SSH_PRIVATE_KEY` | приватный ключ, которым CI входит на сервер |
| `GRAFANA_ADMIN_PASSWORD` | пароль `admin` в Grafana; действует только при первом запуске |

**Variables** — обычные настройки, видны и правятся в интерфейсе:

| | Пример |
|---|---|
| `API_DOMAIN` | `vc-api.knyazushka.ru` |
| `WEB_DOMAIN` | `vc.knyazushka.ru` — домен фронта, его обслуживает этот же Caddy |
| `PUBLIC_APP_URL` | `https://vc.knyazushka.ru` |
| `CORS_ALLOWED_ORIGINS` | `https://vc.knyazushka.ru` |
| `STORAGE_BASE_URL` | `https://vc-api.knyazushka.ru/files` |
| `STORAGE_S3_ENDPOINT`, `STORAGE_S3_REGION`, `STORAGE_S3_BUCKET` | из панели хранилища; адрес — со схемой `https://` |
| `SMTP_ADDR`, `MAIL_FROM` | `smtp.<сервис>:587`, `no-reply@vcard.knyazushka.ru` |
| `SSH_HOST`, `SSH_USER` | IP сервера, `deploy` |
| `SSH_KNOWN_HOSTS` | вывод `ssh-keyscan -t ed25519 <IP сервера>` |
| `RATE_LIMIT_PER_MINUTE`, `RATE_LIMIT_STRICT_PER_MINUTE` | необязательны; без них 100 и 10 |

Отсутствие обязательного значения роняет выкатку до того, как она коснулась
сервера, со списком недостающих имён. Новая переменная окружения
приложения — это ещё и строка в job `deploy` в `release.yml`: список там
явный.

Значения, которые следуют из устройства стенда (`APP_ENV`, адреса
слушателей, `TRUST_PROXY_HEADERS`, `STORAGE_DRIVER=s3`), зашиты
в `deploy/compose.yaml`.

### Выкатка

`push` в `main` → `.github/workflows/release.yml`:

1. те же проверки, что на PR (`ci.yml`): линт, тесты, миграции вверх-вниз
   на настоящем Postgres, сверка кода со спекой;
2. образ `ghcr.io/<репозиторий>:sha-<коммит>`;
3. по SSH: файлы из `deploy/` и env-файлы на сервер, затем
   [`deploy.sh`](../deploy/deploy.sh): `migrator` → `api` → перечитать
   конфиги Caddy, Prometheus и Grafana → ждать `/readyz`.

Изменения только в `docs/` и `*.md` выкатку не запускают.

**Откат** — Actions → release → запуск с нужным коммитом → *Re-run jobs* →
`deploy`. Каждый job выкатывает образ своего коммита, образы в реестре
не удаляются. Миграции при этом не откатываются — ещё одна причина держать
их совместимыми с прежним кодом.

### Мониторинг

Prometheus и Grafana живут на том же сервере. Prometheus собирает метрики
api раз в 15 секунд и хранит 30 дней. Grafana слушает только
`127.0.0.1:3000`, наружу не опубликована — вход через SSH-туннель:

```bash
ssh -N -L 3000:127.0.0.1:3000 <вы>@<IP сервера>
# и открыть http://localhost:3000, логин admin
```

Так не нужны ни домен, ни сертификат, ни публичная админка с паролем,
который перебирают боты. Если понадобится доступ без SSH — блок
в `deploy/caddy/Caddyfile` со своим доменом и `reverse_proxy grafana:3000`.

Источник данных и дашборд `vcard` заводятся из файлов в `deploy/grafana`.
Изменённый файл Grafana на лету не перечитывает, поэтому `deploy.sh`
перезапускает её после каждой выкатки — секунд десять без графиков,
метрики тем временем собирает Prometheus. Правки дашборда в интерфейсе
не сохраняются: изменения — через JSON в git (Export → Save to file).

`GRAFANA_ADMIN_PASSWORD` Grafana читает, только когда создаёт
администратора, то есть при самом первом запуске. Сменить пароль потом —
в интерфейсе или командой
`docker compose exec grafana grafana cli admin reset-admin-password <новый>`.

## Локальный прод-стенд

Тот же `deploy/compose.yaml`, что на сервере, и образ из рабочей копии.
Вместо управляемых сервисов — контейнеры: Postgres, MinIO вместо S3,
Mailpit вместо почтового сервиса. Всё отличие от прода —
в [`deploy/local/compose.override.yaml`](../deploy/local/compose.override.yaml).

```bash
make stand-up       # или: sh deploy/local/up.sh
make stand-smoke    # или: bash deploy/local/smoke.sh
bash deploy/local/traffic.sh 15   # трафик для графиков, 15 минут
make stand-down     # остановить и удалить данные стенда
```

`up.sh` повторяет `deploy.sh` по шагам: сборка образа, миграции, запуск,
перечитывание конфигов, ожидание `/readyz`. `smoke.sh` проходит через Caddy
по HTTPS всё, что зависит от окружения: refresh-cookie, загрузку в S3
и раздачу через `/files`, отрисовку карточки, письмо до Mailpit, CORS,
оба лимита, метрики.

| | Адрес |
|---|---|
| API | `https://localhost:8443/api/v1` — сертификат самоподписанный, `curl -k` |
| Фронт | `https://vc.localhost:8443` — поднимается из репозитория фронта, `sh deploy/local/up.sh` |
| Grafana | `http://localhost:3030`, `admin` / `local-admin` |
| Mailpit | `http://localhost:8026` |
| Пробы и метрики | `http://127.0.0.1:9091` |

Порты сдвинуты, чтобы стенд уживался с окружением разработки: 3000 займёт
фронт, 9090 — `make run`, 8025 — Mailpit из `docker-compose.yml`. У стенда
своё имя проекта (`vcard-local`), и `stand-down` окружение разработки
не трогает.

Что стоит знать:

- **Нужен Docker Compose 2.30+** — ради `env_file` с `format: raw`.
  На старом `up.sh` откажется запускаться с понятным сообщением; обновите
  Docker Desktop или укажите свежий бинарь: `COMPOSE=/путь/к/docker-compose`.
- Повторный `smoke.sh` — не раньше чем через минуту: он исчерпывает лимиты.
- Сценарии рассчитаны и на Git Bash под Windows: тела с кириллицей
  передаются из файла, подмена путей выключена.
- Образы MinIO удалены с Docker Hub; на quay.io остались, версия закреплена.

## Остановка

По SIGINT/SIGTERM процесс перестаёт принимать новые соединения, даёт доработать
текущим и по истечении `HTTP_SHUTDOWN_TIMEOUT` (15 с) рвёт принудительно.
Останавливаются оба сервера и почтовый воркер. Docker ждёт 20 секунд
(`stop_grace_period`) — дольше этого таймаута, иначе процесс убивался бы
посреди корректной остановки.

Письмо, взятое в работу и не отправленное, вернётся в очередь: аренда
в `email_outbox` истекает, и следующий тик заберёт его снова.

## Масштабирование

Процесс stateless при `STORAGE_DRIVER=s3`, и вторую реплику можно поднять
без правок кода. Две оговорки:

- С `STORAGE_DRIVER=local` реплика должна быть одна: файлы лежат на диске
  процесса. Поэтому локальный диск — только для разработки.
- Лимит частоты считается в памяти процесса: с N репликами он фактически
  умножается на N.

Почтовый воркер к этому готов заранее: `FOR UPDATE SKIP LOCKED` позволяет
нескольким процессам разбирать очередь, не отправляя письмо дважды.

## Что смотреть при инцидентах

**Дашборд** `vcard` в Grafana: сверху сводка — жив ли api, запросы в секунду,
доля 5xx, p95, отказы лимита за час, очередь писем, ожидание соединения
с базой. Ниже — HTTP по операциям, карточки и почта, пул соединений,
память и CPU процесса. У каждой панели есть описание: что значит
отклонение.

**Метрики** — `:9090/metrics`. Кроме стандартных метрик Go и процесса:

| Метрика | Что показывает |
|---|---|
| `vcard_http_requests_total{operation,code}` | запросы по операциям спеки и кодам ответа |
| `vcard_http_request_duration_seconds{operation}` | задержка по операциям |
| `vcard_http_requests_in_flight` | запросы в работе прямо сейчас |
| `vcard_card_render_duration_seconds{format}` | отрисовка карточки, без кэша |
| `vcard_card_cache_hits_total{format}` | карточки, отданные из хранилища |
| `vcard_outbox_emails{status}` | письма в очереди по статусам |
| `vcard_outbox_sent_total`, `vcard_outbox_send_failures_total` | отправленные письма и неудачные попытки |
| `vcard_db_pool_*` | соединения пула и ожидание свободного |

`operation` — `operationId` из спеки, а не путь: в путях UUID и слаги,
и число рядов росло бы с каждым профилем. Особые значения: `files`,
`preflight` и `unknown` — путь, которого нет в API (обычно сканеры).
Отказы ограничителя видны как `code="429"`.

**Логи** — JSON в stdout, на сервере — `docker compose logs api` в
`/opt/vcard` (ротация: 5 файлов по 10 МБ на контейнер). Ключевые поля:
`request_id` (он же в заголовке `X-Request-Id` ответа — по нему клиентская
жалоба связывается с записью), `status`, `duration_ms`.

Уровень ERROR — только настоящие пятисотки. 501 «операция не реализована»
туда не попадает намеренно: иначе уровень стал бы нечитаемым.

Отдельно стоит следить за строкой `refresh token reuse detected` — это признак
кражи токена, а не рутина.

**Очередь писем**:

```sql
select status, count(*), max(attempts) from email_outbox group by status;
```

Письма после шести неудачных попыток переходят в `FAILED` и остаются
в таблице как след для разбирательства; причина — в `last_error`.

## Долги, влияющие на эксплуатацию

1. **Ротации ключа JWT нет** — смена секрета разлогинит всех.
2. **Протухшие сессии не чистятся** — `sessions` растёт с каждым входом.
   Метод `DeleteExpired` есть, воркера нет.
3. **Старые карточки не удаляются.** Правка профиля порождает новый файл,
   прежний остаётся. Место дешёвое, но уборщик когда-нибудь понадобится.
4. **Бэкапы — только те, что делает управляемая база.** Бакет S3
   не копируется никуда.
5. **Алертов нет.** Дашборд показывает проблему тому, кто на него смотрит;
   сам никого не будит.
